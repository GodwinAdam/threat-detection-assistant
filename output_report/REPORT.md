## What input this pipeline accepts, and where to get it from the internet

The agent takes a **raw Sigma detection-rule YAML string** as `raw_rule`
(plus a `caller_id` string). You can get real test input from:

- **[SigmaHQ/sigma](https://github.com/SigmaHQ/sigma)** — the standard
  public repository of community Sigma rules. Scenario 02 below uses a real
  rule pulled live from `rules/windows/process_creation/` in that repo —
  nothing synthetic about it.
- **Your own SIEM/EDR rule exports** — anything that's valid Sigma YAML.
- **Plain text, even non-YAML** — the pipeline doesn't require valid Sigma;
  `parse_sigma_rule` degrades gracefully on bad input instead of crashing
  (see scenario 05).

## Classification legend

The pipeline itself only computes one real number — ATT&CK tag coverage
percentage from `calculate_coverage_gap` — plus a pass/fail governance
decision. The labels below map those two things onto the categories you
asked about; they are not a separate "risk score" the tool invents:

| Label | What it actually means in the code |
|---|---|
| **POSITIVE / LOW RISK (good shape)** | Pipeline completed; every ATT&CK tag the rule declares was confirmed discussed in the LLM's report (`missing_techniques: []`, coverage 100%). |
| **HIGH RISK / GAP FOUND** | Pipeline completed; at least one declared tag was **not** confirmed in the LLM's output (`missing_techniques` non-empty). |
| **NO RISK BASELINE** | Pipeline completed, but there were no ATT&CK tags to grade against at all (either none declared, or the rule didn't parse) — there's nothing to call "covered" or "missing." |
| **NEGATIVE / BLOCKED (governance)** | The governance guard rejected the input before it ever reached the LLM (prompt-injection phrase detected). |
| **NEGATIVE / BLOCKED (access control)** | The `caller_id` wasn't on the configured allow-list — rejected before the rule content was even looked at. |

## ⚠ Real limitation discovered during this run: ID presence ≠ correctness

**Scenario 03's "100% coverage" result is misleading, and I want to flag
that rather than let a clean-looking number stand unexamined.** Its report
labels `T1003.001` as *"Timestomp: Adversaries may modify the timestamp of
a file..."* — that description is wrong. In real MITRE ATT&CK, `T1003.001`
is **"LSASS Memory"** (credential dumping); "Timestomp" is actually
`T1070.006`, a completely different technique. I reproduced the retrieval
step independently to find out why: `hybrid_search` for this rule's query
returned `T1055` (correct) and `T1566.001 - Spearphishing Attachment`
(irrelevant) — **it never retrieved `T1003.001`'s real description at
all**, even though the rule's tags asked for it. With no correct context in
front of it, the LLM filled the gap from its own training memory — and got
it wrong, confusing two similarly-numbered sub-techniques.

**Why this matters**: `gap_node`'s coverage check (`calculate_coverage_gap`)
only verifies that a technique **ID string** like `T1003.001` appears
somewhere in the final report — it has no way to verify the *description
attached to that ID is actually correct*. So "100% coverage" here means
"every declared ID was mentioned," not "every declared technique was
correctly analyzed." Scenario 03 is the concrete proof that those two
things can diverge. Two real fixes this surfaces for next time: (1) raise
`top_k` in `rag_analysis_node` so retrieval is less likely to miss a
tagged technique entirely, and (2) have `gap_node` cross-check the
*retrieved context* was actually used, not just that the ID string appears.
Neither fix is implemented yet — this report exists to surface the gap
honestly, not to paper over it.

## Other honest notes on what actually happened

**Scenario 03 also did not produce a *missing*-technique gap, even though I
designed it to try to** (a separate point from the hallucination above).
I tagged the rule with two techniques (`T1055`, `T1003.001`) where the
detection logic only clearly supports one, expecting the LLM to only
confirm the supported one and leave a gap. It didn't — because the raw
Sigma YAML (including the `tags:` field) is shown directly to the LLM in
the prompt, so at `temperature=0` it reliably reads the tags off the page
and restates them rather than independently re-deriving whether they're
actually supported by the detection logic. **This is a real, honest finding
about the current prompt design, not a failure to report**: if you want the
LLM to genuinely validate tags rather than echo them, the prompt would need
to withhold the tags from the text shown to the model and only use them for
retrieval. Scenario 09 exists specifically because relying on the LLM alone
couldn't guarantee a gap example — the deterministic tool call can.

**Scenario 07's "INPUT" shown in the `.txt` file is the rule *as submitted*,
not what the LLM actually saw.** The audit log (`audit_log.jsonl`) confirms
two redaction events fired at that timestamp — the API key pattern and the
email pattern — meaning the sanitized version (with `[REDACTED_SENSITIVE_DATA]`
in place of both) is what actually reached the LLM. I'm calling this out
explicitly so the report isn't misread as "the secret was sent to the model."
